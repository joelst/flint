## Notes for design

### Co-residency confirmed

Both models (phi-4-mini ~4.9 GB + mistral-7b ~4.2 GB) loaded simultaneously with no eviction.
RSS peaked at 10.37 GB and stayed flat — Foundry Local did not evict A when B was loaded.
`aIsLoaded` remained `true` throughout. Optimistic `Map<alias, model>` pool design is viable.

### HTTP routing requires variant ID, not alias

The Foundry Local OpenAI-compatible endpoint routes requests by **model variant ID**, not by catalog alias.

- Requests with `model: "phi-4-mini"` → HTTP 400 "not loaded"
- Requests with `model: "Phi-4-mini-instruct-generic-cpu:5"` → HTTP 200 ✓

The pool must store the resolved variant ID alongside the alias and use `variantId` (not `alias`) in outbound HTTP requests to the local service.

External tools connecting to Flint's endpoint also need the variant ID in their `model` field. The Integrations tab snippets need to document how to discover the correct variant ID (e.g. via `GET /v1/models` or Flint's copy-to-clipboard in the model detail panel).

### Variant selection resolved to generic-cpu despite CUDA EP registration

Despite `CUDAExecutionProvider` registering successfully, `catalog.getModel()` resolved both models to `generic-cpu` variants (`Phi-4-mini-instruct-generic-cpu:5`, `mistralai-Mistral-7B-Instruct-v0-2-generic-cpu:3`). CUDA variants (`Phi-4-mini-instruct-cuda-gpu:5` per `foundry cache list`) appear to be cached under a different app context or Foundry Local path than what the `flint` appName uses. Does not affect the co-residency or routing conclusions — both variants ran and served chat requests correctly.
